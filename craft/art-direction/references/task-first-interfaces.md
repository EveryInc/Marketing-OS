# Task-first interfaces

Use for interactive schedules, portals, asset libraries, and working dashboards. Apply
only the relevant checks to a narrow repair. This guide adds interface-specific decisions
to the existing task-context, design-foundations, and design-review rules. It does not
replace strategy, authorize deployment, or require a new brand process.

## Establish the job before choosing the layout

Translate the request into concrete questions and actions: what happens when and where;
who is involved; which file to use; how to replace it. Put each proposed section against
one of those jobs. Omit sections that have no requested or necessary purpose. Completion
counters, approval queues, and readiness scores need their own user need and dependable
data; the word “dashboard” does not imply them. An analytical dashboard may need metrics
first. A working schedule usually needs the schedule first.

When feedback rejects the product model, rewrite the brief before another visual pass.
A smaller status panel still fails if the user rejected status reporting. Keep explicit
exclusions alongside the required actions. Do not broaden the scope to fix an unrelated
problem discovered during research.

## Let source relationships shape the interface

Use current authoritative sources to distinguish the entities before drawing screens.
An official program, team logistics, a session asset, and a shared production library may
have different dates, owners, and editing rights. Give them appropriate views and links;
do not flatten them into one undifferentiated list.

Record the source, checked date, and owner for consequential fields. Decide where each
field can be changed. A sourced snapshot must say so; it must not imply live synchronization.
If another document remains canonical, link corrections there or implement an explicitly
authorized synchronization path. Local edits must not silently overwrite that authority.
Preserve existing team edits when refreshing imported data and surface conflicts.

Distinguish a source folder, working concept, attached file, and approved deliverable.
Presence alone proves neither readiness nor approval. Mark missing or tentative facts
where they affect a decision. Do not infer durations, deadlines, or completion from layout.

## Apply the approved identity to the job

Inspect the supplied live site and editable brand sources. Inherit the exact marks,
fonts, color roles, and components that govern this work; identify any missing dependencies.
Preserve distinctive expression while adapting density and behavior to the working task.
A campaign hero or background texture may belong on a public page and obstruct an internal
schedule. Copy the useful visual rules, not every feature of the reference page.

Use a structural reason for the layout: aligned start-time rows when simultaneity matters,
a dated list for sparse logistics, contextual detail when users need to keep their place.
These are choices, not mandatory components. Prioritize the core task in the first viewport;
keep secondary source notes available through progressive disclosure. On small screens,
reflow the structure and check essential text at its displayed size instead of shrinking
the desktop layout. Use design-foundations for contrast, typography, focus, and controls.

## Prove access and complete actions

Before committing to hosting or a sharing design, establish who must view, edit, and
upload, which sign-in they can use, and what must stay private. Check the destination's
capabilities early. A workspace-wide audience setting does not prove that every intended
teammate can enter. If required access is unsupported, flag the blocker before polishing
or promising delivery. Never make private material public to remove a login step.

For requested interactions, specify the complete loop and test it within authorized scope:

- Find an entry, open its information, and return without losing useful context.
- Add or replace a file or link, review the result, save, and confirm it survives reload.
- For shared editing, confirm an authorized non-owner can perform the permitted action
  and another admitted session can see the saved change. Browser-only storage is not
  shared persistence.
- Exercise relevant empty, error, pending, cancelled, and conflicting-edit states. Preserve
  unsaved input and existing data; avoid irreversible replacement without recovery.

A link field does not fulfill a requested upload. A thumbnail does not prove the file
opens for a teammate. Local test identities prove local behavior only. If a deployed
non-owner login cannot be tested, mark it unverified and state the smallest remaining
access check. Do not describe the tool as fully ready while a core action is blocked.

Use the applicable engineering workflow for implementation and data safety; visual
guidance does not replace those checks. When independent agents or reviewers are
authorized and useful, give them bounded questions and a shared brief. Keep one integrated
result. More agents, review labels, or elapsed time are not evidence of better work.

## Review the experience and keep the evidence bounded

Inspect the rendered result using the intended user's tasks. Fix the most consequential
observed failure and inspect that same condition again. Include a dense entry, missing
information, mobile use, and the requested editing flow when applicable. A build or unit
test pass cannot establish comprehension, visual finish, or deployed access.

Handoff the usable link or editable artifact, what was verified, and remaining blockers.
Separate visual approval, functional verification, and audience access. Keep blockers
prominent; an attractive screenshot cannot cancel one.

When the user prefers a revision, compare the artifacts and name the observable changes.
Keep the evidence in project context and promote only bounded rules through learning-loop.
That preference supports the current result; it does not isolate the cause or prove faster
future work. Use design-review's correction-round metric and defect guardrails on the next
authorized comparable assignment. Do not invent a baseline or an extra project to claim
transfer.
